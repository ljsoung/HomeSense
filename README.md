# HomeSense

> 국토교통부 실거래가 데이터를 배치로 수집·매칭해, 관심 매물·지역의 시세 변동을 알림으로 받아볼 수 있는 개인화 부동산 시세 조회 서비스입니다.

HomeSense는 국토교통부 실거래가 Open API 수집부터 법정동·단지 매칭, 회원 인증·개인화, 조건 기반 알림, 캐싱을 통한 성능 개선까지 하나로 이어지는 흐름을 Spring Boot(백엔드)와 React(프론트엔드)로 구현하는 솔로 개발자(지성)의 포트폴리오 프로젝트입니다.

단순한 시세 조회 대시보드에 그치지 않고, 대용량·다종 공공데이터의 배치 처리와 정합성 설계, 인증·개인화, 알림, 캐싱, 지도·좌표 데이터 처리까지 실무형 풀스택 아키텍처 역량을 증명하는 것을 목표로 삼았습니다.

아파트·연립다세대는 동일한 단지 마스터 데이터를 공유하고 지번 기반 정밀 매칭이 가능한 반면, 오피스텔·단독다가구는 서로 다른 매칭 전략(텍스트 매칭 / 읍면동 집계)이 필요합니다. 이 데이터 특성 차이를 반영해 매칭 전략이 동일한 아파트·연립다세대를 MVP로 확정하고, 나머지 두 유형은 향후 확장 단계로 분리했습니다.

## 해결하려는 문제

부동산 실거래가는 국토교통부가 공개하지만, 원본은 유형별로 흩어진 XML 응답과 텍스트 주소뿐이라 특정 단지의 시세를 지도 위에서 한눈에 보거나 원하는 매물의 가격 변동을 자동으로 추적하기 어렵습니다.

HomeSense는 다음 흐름으로 이 문제를 해결합니다.

1. 국토교통부 실거래가 Open API에서 아파트·연립다세대의 매매·전월세 데이터를 배치로 수집합니다.
2. 법정동코드와 단지 기본정보 마스터를 기준으로 지번 단위 정밀 매칭을 수행합니다.
3. 매칭된 매물의 주소를 좌표로 변환해 지도 기반 검색을 제공합니다.
4. 회원이 관심 매물·지역을 등록하면, 배치가 조건을 평가해 가격 변동·신규 거래를 알림으로 전달합니다.
5. 자주 조회되는 지역·단지 데이터는 캐싱해 응답 속도를 개선합니다.

## 주요 기능

### 배치 데이터 수집과 매칭 파이프라인

- 국토교통부 실거래가 Open API 4종(아파트·연립다세대 × 매매·전월세) 배치 수집, 초당 30건 제한 대응 스로틀링
- Open API 에러코드(01~32)별 CONTINUE / RETRY / ABORT_BATCH 판정과 부분 실패 허용 — 특정 유형·지역·기간 실패가 전체 배치를 중단시키지 않음
- 법정동코드 CSV(CP949, 문자열 고정) 매핑과 폐지 코드 필터링
- 시도·시군구·동리 1차 필터링 후 지번 정규식 추출로 단지 마스터 매칭(EXACT / SIMILAR 판정, 목표 성공률 98.9% 이상)
- `dedup_hash` 기준 upsert로 중복 적재 방지
- 카카오맵 REST API 지오코딩, 단지·건물 단위 캐싱으로 중복 호출 방지

### 실거래가 조회와 지도 검색

- 지역·단지·주택유형(아파트/연립다세대)별 실거래 검색, 매매/전세/월세 구분 조회
- 단지 상세 — 기본정보에 더해 "상세정보 보기" 토글로 관리방식·승강기·주차/전기차·보안편의시설 등 확장정보 노출
- 카카오맵 기반 매물 지도 조회, 마커 클러스터링, 지도-목록 연동 보기
- 매칭 방식(정확/유사)과 좌표 정밀도(정밀/근사)를 배지로 명시해 데이터 신뢰도를 투명하게 표시

### 개인화와 알림

- JWT 기반 인증(Access/Refresh) — 비로그인 조회는 전면 허용하고, 관심 등록 등 개인화 액션 시점에만 로그인 유도(요청 컨텍스트 보존)
- 관심 매물·관심 지역 등록/해제, 가격 변동 임계치·신규 거래 알림 조건 설정
- 배치 완료 후 조건 평가 → 이메일(AWS SES) 알림 발송 → 알림 이력에서 변동 내역으로 딥링크

### 운영과 성능

- Redis 기반 조회 캐싱(`@Cacheable`/`@CacheEvict`), 배치 적재 완료 시 관련 캐시 자동 무효화
- Controller-Service-Repository 3계층 구조, 전역 예외처리기와 표준 응답 포맷(`ApiResponse<T>`)으로 일관된 API 계약 유지
- 배치 실행 이력 모니터링과 수동 재실행(선택 범위)

| 컴포넌트 | 책임 |

| 공통기반 (Common) | JWT 인증, 전역 예외처리, Redis 캐시 설정, 로깅, 설정관리, 응답 포맷, 입력검증 |
| MariaDB 10.11 | 11개 테이블 영속 저장소 (회원·기준정보·실거래·개인화·알림·운영 도메인) |
| Redis | 단지 상세·인기 단지·지역 자동완성 등 조회 결과 캐싱 |

## 주요 설계 결정

### CHECK 제약과 FK `ON UPDATE` 정책을 함께 검토

MariaDB에서 `CHECK` 제약과 `ON UPDATE CASCADE`를 같은 테이블에 함께 사용하면 실제로 에러(1901)가 발생함을 로컬 인스턴스에서 확인했습니다. 이 프로젝트는 PK가 전부 서로게이트 키라 애초에 PK 변경이 발생하지 않으므로, 모든 FK의 `ON UPDATE`를 `RESTRICT`로 통일해 문제를 근본적으로 피했습니다.

- 근거: 테이블 정의서 v2.0 4장(참조무결성 목록), CLAUDE.md 설계 원칙

### 사용하지 않는 컬럼은 DB에 추가하지 않는다

`complex` 테이블은 원본 단지 기본정보 85개 컬럼 중 41개만 채택했습니다. 이후 DTL-01 "상세정보 보기" 토글 설계가 확정되면서 실제로는 쓰이지 않게 된 컬럼 4개(`eup_myeon`, `road_address`, `zip_code`, `registration_date`)를 뒤늦게 발견해 실 DB에서 제거하고 스키마를 재검증했습니다. "나중에 쓸 수도 있으니" 컬럼을 미리 만들지 않는다는 원칙을 이때 확정했습니다.

- 근거: 엔티티 정의서 v2.0 7장(소스-타겟 매핑), 7.1절(채택 후 제거 이력)

### 매칭 전략이 같은 유형만 MVP로 묶는다

아파트·연립다세대는 동일한 단지 마스터와 지번 기반 매칭 로직을 공유하지만, 오피스텔은 별도 단지 마스터가 없어 텍스트 매칭이 필요하고, 단독·다가구는 법령상 지번이 일부만 공개돼 읍면동 단위 집계에 의존해야 합니다. 서로 다른 매칭 전략을 한 번에 검증하기보다, 매칭 전략이 같은 두 유형만 먼저 MVP로 완결하고 나머지는 향후 확장 단계로 분리했습니다.

- 근거: 요구사항 정의서 v3.0 1.1절·10장, 엔티티 정의서 v2.0 3.1절

### 단지코드 크로스워크 없이 텍스트 매칭만으로 해결

시도·시군구·동리로 1차 필터링한 뒤 법정동주소의 지번을 정규식으로 추출해 매칭하는 방식만으로 목표 성공률(98.9% 이상)을 만족할 수 있음을 확인해, 별도의 매매전월세 단지코드 크로스워크 파일을 도입하지 않기로 했습니다.

- 근거: 요구사항 정의서 v3.0 FR-2.5, 6.2절

## 진행 상황

현재 설계 단계를 완료하고 구현 단계에 진입한 상태입니다.

- 설계 문서 6종 완성 — 요구사항정의서 v3.0, 엔티티정의서 v2.0, 테이블정의서 v2.0, UI정의서 v2.1(화면 15종), 프로그램목록서 v2.0(프로그램 60종), 프로그램설계서 v2.0
- DB 스키마(11개 테이블 · 161개 컬럼 · FK 17건 · CHECK 10건 · UNIQUE 8건)는 로컬 MariaDB 10.11 인스턴스에 DROP → CREATE 전체를 실행해 오류 없이 생성됨을 검증했습니다.

요구사항 정의서 9장의 5단계 MVP 로드맵에 따라 순서대로 구현합니다.

| 단계 | 단계명 | 신규 프로그램 | 핵심 내용 |
| --- | --- | --- | --- |
| 1단계 | 핵심 검증 (아파트 중심) | 42종 | 인증, 단지·실거래 배치/매칭/조회, 캐싱 |
| 2단계 | 연립다세대 확장 | 0종 | 1단계 프로그램의 `housingType` 적용 범위만 확장 |
| 3단계 | 지도 기반 조회 | 2종 | 지오코딩, 지도 화면·API |
| 4단계 | 개인화 (관심·알림) | 9종 | 관심 매물·지역, 알림 설정·발송 |
| 5단계 | 선택 범위 | 7종 | 유형별 시세 비교, 관리자, 소셜 로그인 |
